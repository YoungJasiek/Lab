1. Architecture: Decentralized Standalone Plugins (Unity & Blender Model)

In modern game engines like Unity (Package Manager) and 3D suites like Blender (Python Addons), extensibility is built upon isolated, self-contained modules. Previously, scripting logic in Lab was centralized inside shared engine script folders.

The Modular Drop-in Plugin Architecture strictly separates plugins into distinct, standalone code units:

  • Complete Isolation: Every plugin lives in its own dedicated .lua file inside the root plugins/ directory. There are no monolithic script merges or hardcoded engine dependencies.
  • Self-Describing Metadata: Each plugin script declares a standardized metadata dictionary (name, id, version, author, category, description) at the top of the file.
  • No Compilation Required: Drop a new .lua file into plugins/ and the engine immediately discovers, validates, and integrates it into the editor menu and simulation pipeline.
  • Non-Intrusive Engine Core: Disabling or removing a plugin leaves the core engine and project assets completely unaffected.

2. Dynamic Discovery & Folder Structure

Plugins are compiled as independent C++ dynamic shared libraries (plugins/*.dll), cleanly separated from engine core libraries and game logic: 

Lab/
├── engine/              # Engine-internal shaders, fonts and fallbacks
├── games/               # Separated game projects (e.g. games/frozen_life/)
├── plugins/             # Standalone Compiled Native C++ DLL Plugins
│   ├── ai_patrol.dll          # Waypoint patrol & bot sensory perception
│   ├── arcade_vehicle.dll     # Raycast suspension & vehicle dynamics
│   ├── cloth_physics.dll      # Verlet integration & cloth physics
│   ├── constraints_joints.dll # Constraints, hinges & joint dynamics
│   ├── dialogue_quest.dll     # NPC dialogue trees & quest tracker
│   ├── discord_rpc.dll        # Discord Rich Presence bridge
│   ├── dropin_example.dll     # Minimal C++ plugin template (ILabPlugin)
│   ├── fluid_buoyancy.dll     # Water simulation & Archimedes buoyancy
│   ├── force_fields.dll       # Blast shockwaves & vortex force fields
│   ├── procedural_level.dll   # Procedural CSG room generator
│   ├── retro_shaders.dll      # Retro CRT & scanline post-processing
│   ├── speedrun_timer.dll     # Speedrun splits & HUD telemetry
│   └── voxel_terrain.dll      # Dynamic voxel terrain & volume sculptor
├── src/plugins/         # Native C++ source code for each plugin
└── build/Release/       # Standalone executables (LabEditor.exe, LabPlayer.exe)

When Lab::PackageManager::scanPluginDirectory("plugins") executes, it discovers all *.dll files, calls Win32 LoadLibraryA + GetProcAddress("CreatePlugin"), registers their ILabPlugin instances and manages their lifecycle with zero interpreter overhead.

3. Plugin Lua API & Life Cycle Callbacks

Every drop-in plugin defines standard life cycle hooks that the engine invokes during editing and gameplay ticks:

Callback Function Arguments Trigger & Description
onLoad() none Invoked when the plugin is activated or hot-reloaded. Use to initialize data structures, subscribe to engine events, or allocate state.
onUnload() none Invoked when the plugin is disabled or prior to hot-reloading. Cleans up geometry, HUD elements, or background threads.
onUpdate(dt) dt (number, seconds) Called every physics/simulation tick during Play-In-Editor (PIE) and runtime gameplay.
onRender() none Called during the viewport rendering pass for custom gizmos, debug lines, or screen overlays.
onEditorGui() none Called when the user selects the plugin in the Package Manager or inspector to render custom controls.

Standard Metadata Schema

A drop-in plugin starts with a declarative table returned or exported as Plugin:

-- plugins/my_custom_plugin.lua
Plugin = {
    name        = "Custom Speed Teleport",
    id          = "com.user.teleport",
    version     = "1.0.0",
    author      = "YourName",
    category    = "Gameplay",  -- Categories: Gameplay, Rendering, AI, Tools, Audio, Network
    description = "Adds instantaneous hotkey teleports and velocity dampening."
}

function Plugin.onLoad()
    print("[Custom Plugin] Initialized!")
end

function Plugin.onUpdate(dt)
    -- simulation logic
end

function Plugin.onUnload()
    print("[Custom Plugin] Cleaned up!")
end

return Plugin

4. In-Engine Package Manager GUI

Accessing Plugins > Package Manager in LabEditor.exe opens the visual management suite inspired by Unity's Package Manager and Blender's Preferences > Add-ons modal:

Package Manager Capabilities

  • Live Search & Filter: Type to search by name, ID, author, or description. Filter by category pills (All, Gameplay, Rendering, AI, Tools, Social).
  • Instant Toggle Checkbox: Enable or disable any plugin on-the-fly. The engine immediately invokes onUnload() or onLoad() without requiring an editor restart.
  • Hot Reload Button: Reload modified Lua files from disk immediately to iterate without closing the level.
  • Active State Persistence: Enabled/disabled states are stored in plugins.config, ensuring user preferences survive editor restarts.
  • Direct Source Jump: One-click button to open the plugin's source file in the built-in Scripting IDE.

6. Step-by-Step Native Plugin Authoring Guide

Creating a new compiled C++ DLL plugin requires only three simple steps:

  1. Create a source file inside src/plugins/ (e.g., my_plugin.cpp): 
    #include "LabPlugin.h"

namespace Lab {
class MyPlugin : public ILabPlugin {
public:
    const char* getName() const override { return "My Plugin"; }
    const char* getVersion() const override { return "1.0.0"; }
    const char* getId() const override { return "com.community.my-plugin"; }
    const char* getAuthor() const override { return "Developer"; }
    const char* getCategory() const override { return "Tools & Utilities"; }
    const char* getDescription() const override { return "Custom native plugin."; }

    bool onLoad() override { return true; }
    void onUpdate(float dt) override { (void)dt; }
    void onUnload() override {}
};
}

LAB_PLUGIN_EXPORT Lab::ILabPlugin* CreatePlugin() {
    return new Lab::MyPlugin();
}
  2. Compile to a shared library producing plugins/my_plugin.dll.
  4. Open LabEditor: Navigate to Plugins > Package Manager. Your plugin will appear with its category, version badge, and full description, and can be toggled or reloaded dynamically!

7. Dynamic Linking, Memory Safety & Lifecycle

To ensure stability, the native plugin engine incorporates robust fault-isolation mechanisms:

  • Direct C++ ABI: High-performance direct calls via ILabPlugin virtual table with zero marshaling or interpreted scripting overhead.
  • Clean Memory Ownership: Modules allocate and free resources inside their own DLL runtime boundary, with virtual destructors ensuring no CRT cross-heap leaks.
  • Ordered Unloading: When shutting down or reloading, plugins are unloaded in strict reverse order of registration via Win32 FreeLibrary to guarantee clean teardowns of cross-dependent resources.
  • Decoupled Core: Engine executables (`LabEditor.exe`, `LabPlayer.exe`) link only against core interfaces and discover plugins dynamically at runtime.
