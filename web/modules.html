1. Architecture Overview & Decoupling Goals

The Lab Engine eliminates monolithic codebase pitfalls by establishing strict boundary interfaces across 10 specialized dynamic link libraries. This architectural decision delivers multiple engineering advantages:

  • Incremental Compilation: Modifying rendering shaders or HUD logic only recompiles LabRender.dll or LabWorld.dll, avoiding engine-wide re-linking.
  • Independent Standalone Repositories: Each subsystem maintains its own Git repository on Desktop, allowing modular testing, versioning, and reuse across tools like LabHammer and LabStudio.
  • Zero Circular Dependencies: Modules form a clean directed acyclic graph (DAG), rooted at LabCore.dll.
  • Safe Hot-Reloading: Subsystems such as LabScript.dll and LabAudio.dll can reload assets dynamically at runtime without disrupting the core 64Hz simulation loop.

3. ABI & LAB_API Export Specification

Every module defines a standard export macro to control symbol visibility across shared library boundaries. Under MSVC, symbols are qualified with __declspec(dllexport) when compiling the module itself and __declspec(dllimport) when included by client code:

// LabExport.h – Unified Dynamic Link Visibility
#pragma once

#if defined(_WIN32) || defined(__CYGWIN__)
  #if defined(LAB_BUILDING_DLL)
    #define LAB_API __declspec(dllexport)
  #else
    #define LAB_API __declspec(dllimport)
  #endif
#else
  #if __GNUC__ >= 4
    #define LAB_API __attribute__ ((visibility ("default")))
  #else
    #define LAB_API
  #endif
#endif

4. CMake Integration & Consumer Linking

Game executables such as Frozen-Life link against the required subsystem libraries via CMake targets. The build system automatically copies all referenced DLLs to the target executable directory post-build:

# Linking engine modules into FrozenLife.exe
add_executable(FrozenLife src/main.cpp)

target_link_libraries(FrozenLife PRIVATE
    LabCore
    LabRender
    LabAudio
    LabPhysics
    LabAnimation
    LabWorld
    LabNetwork
    LabAI
    LabScript
    LabStudioCore
    LabHUDEditorCore
)

5. Subsystem Initialization & Loading Order

During application boot, subsystems are initialized in strict topological order to ensure all foundational dependencies are established before higher-level systems begin allocation:

  1. LabCore.dll: Initialize window context, Win32/GLFW event dispatch, and 64Hz clock accumulator.
  2. LabRender.dll: Query OpenGL 4.5+ DSA profile, allocate cascaded shadow framebuffers, and load shader pipelines.
  3. LabAudio.dll: Start dedicated miniaudio hardware thread and initialize 26 procedural PCM synthesizers.
  4. LabPhysics.dll: Setup spatial broadphase grids and swept-AABB kinematic constraints.
  5. LabAnimation.dll: Initialize glTF 2.0 humanoid rig, bone cache, and viewmodel arms.
  6. LabScript.dll: Open Lua 5.4 virtual machine and load game_mechanics.lua.
  7. LabWorld.dll: Parse .labmap geometry, populate weapon entities, and start HUD.
  8. LabAI.dll & LabNetwork.dll: Spawn combat bots and bind authoritative UDP server sockets.
